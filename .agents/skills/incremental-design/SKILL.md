# Incremental Game Design

## Goal
Make progression change the player's possibilities and decisions, not merely inflate numbers.

## Core questions
1. What does the player actively do before automation exists?
2. Why is that action interesting for more than the first minute?
3. What changes qualitatively as the player progresses?
4. Which constraint creates decisions: time, space, risk, routing, timing, capacity, information, positioning or something else?
5. What does automation remove, and what new decision replaces the removed labor?
6. If there is a reset/prestige, what genuinely new layer or strategy does it unlock?

## Design process
1. Define the smallest repeatable loop without prestige or meta-progression.
2. Identify one felt escalation axis, not just a numeric multiplier.
3. Design upgrades in categories: capability, rule change, new interaction, efficiency, convenience. Prefer the first three.
4. Introduce automation only after the manual action has taught something worth automating.
5. Use additional resources/layers only when they create new tradeoffs.
6. Treat large-number curves as pacing tools, not the game itself.
7. Prototype the first 5-10 minutes before designing hours of progression.

## Red flags
- Most upgrades are only +X%.
- Optimal play is obvious and never changes.
- Waiting is the only meaningful action.
- Prestige merely repeats the same game faster.
- New currencies duplicate old currencies without adding decisions.
- The design relies on future content to make the current loop fun.
